# Harness 追问：从任务语义讲到验证

这页是技术答题方法，不新增已上线承诺。用短回答进入，再沿专题页展开。

## 1. 为什么 Session、Turn、Step 要分开？

Session 保存长期会话及有效配置，Turn 对应用户这一次任务，Step 表示任务内部一次推进。取消、预算和最终结果通常围绕 Turn；定位某个模型或工具异常要继续下钻。

三个类名不是重点，重点是每个对象的责任和状态归属。只有聊天消息，很难判断“这个工具成功了，但本次任务是不是完成”。状态对象存在也不等于它们已全部持久化。见[恢复主文](../03-持久状态与故障恢复.md)。

## 2. 后台 Worker 到底是什么？

它是推进任务的执行者，不一定是一台独立机器。起步可以是服务进程内的异步任务；要支持进程故障后接管，就需要从持久任务中领取执行权并持续校验。

关键问题是：谁能领取同一 Turn，多久失去执行权，旧执行者回来后能否写入，以及它已经发出的外部动作怎么确认。换一个部署名称不会自动解决这些问题。

## 3. 事件可续读，是否意味着任务可恢复？

不意味着。事件记录告诉用户发生过什么；恢复还需要知道下一步允许做什么、谁能做、上一步副作用是否已提交。前端按游标续读和事件 ID 去重，只恢复观察通道。

如果状态和待发布事件要求一致，可以在同一事务里保存，再异步发布；不能从“SSE 可重连”推断项目已经实现这种事务协议。

## 4. 工具成功后进程崩溃，为什么不能直接重试？

外部动作可能已经发生，本地只是没保存结果。例如作业已经创建，再发一次会多出一个作业。调用前固定操作身份，调用后保存外部回执；恢复优先按幂等键或查询接口确认。

本地 pending 只能说明尚未确认，不能证明尚未发送。既不能查询又不支持去重时，保留结果未知并请求人工处理，比把未知误判为失败更正确。

## 5. Approval 为什么不能只是一个等待回调？

进程里的回调随进程消失。审批应绑定任务、动作、参数摘要、权限版本和审批主体，决定保存后只消费一次。恢复查询原审批，不能重新问一个语义不同的问题。

用户批准执行某个动作，不代表允许任意变化后的参数。资源和动作发生变化，要重新判断授权。Question 则是补充信息，它影响计划，但不自动授予高风险权限。

## 6. 看到 150 次工具调用，第一反应是什么？

先看是否完成了有效工作。分析许多文件可能确实需要大量调用；相同参数反复报错、已有结果却反复检索，才提示循环失控。还要区分 Step、顶层工具调用和工具内部子调用。

先沿轨迹检查结果是否进入模型、原文引用是否可读、压缩是否丢了进度，再用多维预算限制最大损失。固定重复次数要用合理轮询和正常长任务作反例测试。见[执行预算](../02-Harness与执行预算.md)。

## 7. 上下文重构为什么不只是“加一个摘要”？

摘要只减少文字，未必解决谁组装请求、保留什么事实和重启后如何复现。统一装配入口应接收结构化来源，保留工具调用与结果配对，保护目标和权限，再做预算与压缩。

原始结果留下，模型使用受预算控制的视图；原文引用必须能从实际工作区读取。同一输入和策略能得到一致装配，不等于模型每次生成完全相同。见[上下文专题](../04-上下文与Memory.md)。

## 8. 设计百万终端系统，你先问什么？

百万是注册设备、在线连接，还是并发运行任务？提交速率、平均执行时间、端侧依赖和外部写操作分别占多少？这些决定连接、模型和沙箱三个不同的容量问题。

任务入口可靠受理，状态独立保存，执行者按资源准入和所有权推进。队列可以削峰，但消费者仍需检查取消和版本。需要端侧操作的步骤在设备离线时等待，不无条件重放旧命令。这是系统设计，不是已有规模陈述。

## 9. 多副本与任务高可用有什么区别？

多个 API 实例提高接入可用性；任务高可用还要求执行状态可恢复。会话路由能减少请求落错实例，实例真正消失后仍要依赖持久状态和接管。

控制面恢复资源，也不代表恢复了 Python 进程。发布要验证旧任务、新旧格式、停止领取与在途动作，不能只看健康接口。容量和故障讨论见[Infra 排障](../../infra/07-容量压测与故障定位.md)。

## 10. 怎样证明改动确实让 Agent 变好？

固定任务、模型、环境和预算，保存轨迹与成果，由独立验证逻辑检查结果。先分类失败，提出一个主要改动，再比较基线与候选的重复运行及留出任务。

总耗时下降但完成率下降，不能直接算优化；环境安装失败也不能说成模型能力不足。Harbor 的试验结果和 Supervisor 的过程建议分开，不能让后者改写客观分数。见[评测专题](../07-Harbor评测与持续改进.md)。

## 11. 存储升级失败，回滚镜像就够了吗？

不够。还要看旧版本能否读取新写入，以及升级后新增审批、工具回执和文件引用是否仍被保留。回到旧备份可能让刚确认的动作丢失记录，随后被重复执行。

先扩兼容结构、迁移与核对、再切读路径，最后清旧格式。验证迁移中断、新旧实例并存和新任务已产生三种情况。文件与数据库要一起演练恢复，不能只有备份成功日志。

## 12. 你怎么把架构改造落地？

先选可独立验收的链路，做小步切换。例如新旧上下文装配对同一输入做对照，再逐个替换入口；输出物化则从原文保存到下一轮读取一起验收。

每阶段明确兼容和回退方法。证据包括差异、测试、发布范围和残留限制。说“我们做了重构”不如说明一次切换怎样发现问题、如何确认没有回归。
