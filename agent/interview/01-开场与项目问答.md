# 开场与项目：可以直接练习的回答

这是口述底稿，不是要求逐字背诵。完成度和数字以[证据页](03-事实边界与证据.md)为准。

## 1. 请做一下自我介绍

> 面试官您好，我叫廉威，有六年研发经验。之前在华为做 Go 后端和云服务，积累比较多的是服务设计、高并发和线上问题处理。到上海智算后，我先参与云端 AI 产品，重点做自研 Harness 的架构和研发，后来又参与了 YiBuddy 的端侧 Agent。
>
> 我做 Agent 时关注的是任务怎么真正完成。用户提出目标以后，系统可能要反复调用模型和工具、运行脚本、处理文件，最后还得把成果交给用户。这里面最容易出问题的是几个交接处：工具说成功了，文件是否真的可读；页面断开了，后台任务还在不在；执行超时了，能不能直接重试。我主要围绕这些问题做运行时设计、沙箱接入和联调。
>
> 我希望继续做 Agent 运行底座相关的工作，因为这部分既需要架构判断，也需要进入代码和测试验证。我更擅长沿一条任务把问题查清楚，而不是只把模型和工具接通。

30 秒版只保留经历顺序、当前主线和一个代表性问题。六年是本次整理时的履历自述，后续随真实时间更新。

## 2. 你从传统后端转到 Agent，原来的经验有什么用？

> 最有用的是处理状态和异常的习惯。以前一次请求超时，我会问服务端到底有没有处理成功；做 Agent 后，一次任务会包含很多这样的调用，问题反而更多。模型可以建议下一步，但是否允许执行、结果是否确认、失败能否重试，仍然需要系统给出确定答案。
>
> 新增的难点是模型输出并不稳定。不能把所有异常都交给模型“再想一次”，而要给它可修复的工具反馈，并对重复尝试设置边界。我的后端经验主要用在这里。

追问时区分：异步任务解决请求不用一直等；持久化与接管协议才解决执行进程消失后谁继续。

## 3. 三个项目是什么关系？

> 智算云把 Agent 做成云上的服务，重点是任务执行和资源交付；AI4S 是科研垂直方向，专业资料、工具和结果验收更重要；YiBuddy 更靠近用户工作助手，关注真实设备、工作区和用户怎样控制过程。
>
> 它们会遇到一些共同问题，但不能强行说成完全相同的实现。我希望复用的是工具接口、事件和工作区这类有稳定语义的能力，业务规则与端云约束仍然分别处理。

各讲一句后停下来，让面试官选择深入哪个。[完整项目页](../projects/README.md)用于后续追问。

## 4. 智算云和普通聊天应用差在哪里？

> 聊天界面主要交付一段回答，云端 Agent 还要交付实际动作和文件。比如分析一份资料，模型提出运行代码只是开始，还要有环境执行它、确认输出、把结果交回任务，最后让用户能下载。平台需要把这一整条链路组织起来。
>
> 我把它分成三层：云侧服务负责接入和交付，Harness 负责推进任务，沙箱负责隔离执行。三层可以各自演进，但成功和失败的含义必须对齐。不能沙箱返回了接口成功，前端就直接显示报告完成。

不需要通过贬低其他产品来证明价值，限定比较对象是仅调用模型生成文本的实现。

## 5. 为什么 AI4S 不是加了专业 Prompt 的普通 Agent？

> 因为最终验收不一样。综述中的结论要能找到文献来源，数据分析要能说明处理步骤，代码和报告需要能对应。专业 Prompt 可以指导表达，但真正的专业性还得进入工具、方法包和验证规则。
>
> 我负责的是让这些专业能力在平台里有可靠执行路径。领域方法由相关同事提供，平台不应该凭语言流畅就判断科研结果正确。

## 6. YiBuddy 的设计为什么不能直接照搬云端？

> 本机有用户真正的文件、软件和登录状态，能做的事更多，授权也更敏感。云端可以统一配置环境，端侧还要面对休眠、离线和不同用户的机器条件。要重新判断执行放在哪里、哪些数据会上云、设备不在线时任务怎么办。
>
> 可复用的是任务与工具的语义，不能直接照搬的是环境和权限假设。具体哪些已交付，我会按对应版本的验收范围说明。

## 7. 你个人的贡献体现在哪里？

> 我主要负责总体架构和 Harness 主线，也参与核心开发与跨团队联调。不是所有底层组件都由我写，我更直接负责的是任务、工具和执行环境之间的约定能否连起来。
>
> 比如大工具输出在 Web 服务里生成，后续读取却发生在远端沙箱。如果两边的路径没有统一，单个接口都正常，任务仍然失败。我会沿着输出生成、文件同步、模型引用和前端下载把链路验收清楚。具体个人改动，我会拿对应提交和测试说明。

最后一句应在补齐真实材料后展开，不临时编造提交、指标或事故。

## 8. 为什么想继续做 Harness？

> 因为我在产品里反复遇到的核心问题都落在运行底座上。增加一个场景，可能用模板和工具就能开始；但任务跑长了、工具超时了、用户中途离开了，仍然需要同一套可靠的执行规则。
>
> 我希望下一份工作能让我持续对这部分负责，把已有的云服务经验和 Agent 实践做深。吸引我的不是岗位里出现了多少热门词，而是能否长期建设任务执行、资源接入和结果质量这些能力。

投 AI 测试开发时，将末段改为：希望把真实执行经验用于自动化验证和故障分析，帮助团队用可重复证据判断版本质量。前提是愿意承担测试策略、回归和质量交付，不能只强调做 Agent 工具。

## 9. 你的优势和短板是什么？

> 我的优势是能把用户看到的一个“卡住了”，拆成模型、工具、沙箱和展示链路分别验证，也能把架构约定落到代码和测试。当前更扎实的是云侧运行时和执行资源接入。
>
> 模型推理引擎和大规模 GPU 部署是我正在补的方向。我能说明一条推理链路并参与排障，但没有证据的集群规模和调优成果不会写成自己的经历。如果面试测试开发，我也需要补系统的测试策略和质量度量，不能把研发自测直接等同于多年专职 QA。

## 10. 如果被问“你这些很多还没上线”呢？

> 我会按完成阶段回答。主链路有哪些真实运行记录，哪些模块有实现和测试，哪些仍是目标方案，这几类应分开。比如保存事件和展示历史，不能自动证明进程崩溃后能继续工具执行。
>
> 还没有完成的部分，我可以讲清它来自哪个问题，准备修改什么状态和接口，以及如何用故障测试验收。已经完成的部分则拿实际材料说明，不用一张未来架构图覆盖全部现状。
