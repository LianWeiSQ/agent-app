# 智算云：云端 Agent 服务怎样形成交付闭环

[项目总览与架构图](README.md) · [口径边界](../interview/03-事实边界与证据.md)

## 一句话定位

它是一套运行在云上的通用 Agent 服务。用户提交目标和资料，平台完成多轮模型推理、工具调用、代码和文件处理，再提供过程与成果入口。云平台是它使用的基础能力，不是用户必须逐个操作的对象。

## 从一个用户任务讲起

以“分析上传材料并形成报告”为说明例：用户需要的不是模型复述材料，而是能够查看执行进度，知道哪些文件被使用，最终拿到可继续编辑的报告。这是贯穿解释的例子，不代表一个已核验客户案例。

会话建立时确定模板、可用模型与工具、执行模式和工作区。用户发起任务后，Harness 把目标与必要材料送给模型；需要工具时，先检查参数及执行条件，再调用远端能力或沙箱。工具结果进入下一步，事件送到前端，文件通过受控接口交付。

这里有两个平行出口：事件用于展示发生了什么，文件接口用于取得成果。事件显示完成，却找不到文件，不算一次完整交付。

## 三层边界为什么值得单独建设

| 层 | 核心责任 | 不应该代替谁 |
| --- | --- | --- |
| 云侧 Agent 服务 | 身份、项目、配置、任务入口、进度和成果访问 | 不把所有工具差异写入接入接口 |
| Harness | 上下文、模型与工具循环、任务推进与终止 | 不直接在服务宿主环境执行任意模型命令 |
| 沙箱与执行平台 | 环境、命令、文件、资源和回收 | 不负责推断用户目标，也不代替任务状态管理 |

这样划分不是为了组件数量，而是让变化能停在合适的边界。更换执行后端时，仍需要相同的命令结果、文件引用和错误语义；新增业务场景时，优先组合模板、Skill 与工具，不必另写整套运行循环。

## 最能讲深的一个落点：文件引用要真的可读

搜索工具可能在 Web 服务里得到很长的原文。把结果写入本地文件、给模型一个路径，看似完成了输出压缩；但下一轮 read 在远端沙箱执行，这个路径可能根本不存在。

项目准备材料描述了本地与远端输出物化、路径映射和预览下载的接入工作。可讲的工程判断是：只有完整输出在目标环境中可读，才把它作为后续工具可用的引用；同步失败就明确给预览与限制，不能交一个虚假的“全文地址”。

验收应连续执行“工具返回 → 生成引用 → 下一轮读取 → 用户下载”，而不只分别测四个接口返回成功。详见[上下文与大输出](../04-上下文与Memory.md)。

## 个人责任怎么说

准备材料中的主线是总体架构与 Harness 核心设计、研发和联调；沙箱底座、模型服务、产品页面由团队协作完成。重点说明自己在任务对象、执行协议、文件与事件语义上做出的判断，再补具体提交或验收记录。

不要用“整体负责人”替代证据，也不要把底层 Controller 全部写成本人独立实现。

## 完成阶段与下一步

材料陈述模型、工具、沙箱、事件与文件主链路已打通。本轮没有重新部署和验收，因此不据此确认全部线上配置。跨进程接管、完整审批恢复和副作用回执应按模块另行列证，不包含在“主链路打通”里。

下一步材料优先补：一条脱敏任务的输入、工具过程、生成文件及下载结果，关联相同任务标识；再补取消、超时和断线的验收记录。平台价值由交付闭环证明，不由框图上的组件数量证明。
