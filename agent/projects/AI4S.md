# AI4S：通用执行能力怎样服务科研交付

## 它和通用 Agent 的差异

AI4S 是科研垂直方向，不代表整个平台只服务科研。它可以复用会话、工具和执行能力，但“怎样才算做完”要由科研任务决定。

一份综述需要能追溯文献；一次数据分析需要说明输入、处理方法和结果；实验方案需要清楚列出变量、条件和限制。文字流畅只是表达质量，不能代替这些验收要求。

## 一条任务怎样拆

以文献与公开数据分析为说明例：先确认研究问题与材料范围，再通过专业工具获得资料；按需要提取信息，保留来源；执行分析脚本，保存中间数据；最后形成报告，并检查结论与引用能否对应。

领域团队定义方法和质量标准。平台提供有版本的模板与能力包，Harness 推进步骤，沙箱负责执行代码和文件操作。专业性不是往系统提示里多加几段科研术语，而是让领域规则影响工具选择、过程记录和最终检查。

## 为什么它容易暴露运行时问题

材料多，会增加模型输入；依赖多，会拉长环境准备；计算时间长，会考验任务和作业的生命周期；报告需要可追溯，会暴露文件引用与原始证据是否断裂。

因此可以围绕三个判断展开：哪些资料需要全文进入上下文，哪些只保留引用；哪些工作适合会话沙箱，哪些交给作业系统；哪些输出能用代码验证，哪些还需要领域人员复核。具体研究结果的正确性不能由平台工程师单独保证。

## 复用的边界

复用的是输入输出清楚的能力：模型接入、工具执行、工作区与事件格式。领域特有规则留在模板、Skill 和验证逻辑中。两个业务接入同类协议，不等于两套 Harness 已经统一代码。

长计算可以保存外部 jobId 后观察状态；是否已接入某种作业系统，需要实际记录，不能把建议写成既有能力。[GPU 与作业分流](../../infra/sandbox/02-命令文件与恢复.md)进一步解释这个边界。

## 怎样展示开发成果

比单独展示报告首页更有效的是一组对应关系：脱敏输入和研究目标、执行过程、成果页、来源/脚本或验证记录。它们共同说明报告不是孤立生成的一段文本。

当前缺少可公开的这组实图，暂不填入模拟截图。本人贡献继续围绕云侧架构、Harness 及跨层联调展开；专业方法由领域协作提供。没有核验的准确率、科研收益和用户规模不写。
