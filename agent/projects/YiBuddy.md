# YiBuddy：工作助手与端云边界

## 定位与版本先说清

本人后续更正把 YiBuddy 放在端侧 Agent 经历中；准备文档又包含通用工作台、专家协作和云端执行的设计范围。这两部分不能不加区分地拼成一个已经交付的产品版本。

现阶段用“工作型 Agent / 端侧工作助手”作为经历主线；涉及具体 UI、执行位置和 P0 完成度时，需绑定同一个版本的设计与验收。本文没有推断所有命令都在本机执行，也没有把早期规划当成现状。

## 用户面对的是一个连续的工作过程

用户提供目标和资料，选择合适的能力，看到计划和工具过程，必要时补充信息或终止，最后预览、编辑或下载成果。重点不是把多个聊天机器人摆在页面上，而是前后步骤能使用同一批资料，成果也能继续被使用。

例如整理资料时，下载文件、清洗脚本、汇总报告应该属于同一个工作过程。工作区解决文件组织，任务状态解释执行到了哪里，权限控制决定能触碰哪些文件和应用；三者不能互相替代。

## 端侧新增的约束

用户设备有自己的软件、目录、凭据和资源限制。执行前需要说明范围，不能因为 Agent 在本机运行就默认拥有用户全部权限。休眠、离线、应用退出也不同于一次普通接口超时。

模型与外部工具可能在云端，本地文件与操作可能在端上。需要明确哪些资料会外发、哪些动作必须在设备在线时进行，以及离线后任务是等待还是继续云端部分。这里描述的是设计检查项，不声明已经实现全部端云接管协议。

## 为什么先采用固定协作

准备材料中的 P0 方案采用牵头专家与有限成员专家：主任务负责拆分和验收，成员在明确输入、输出、文件范围和预算内工作。独立资料可并行，依赖前一步结果的工作仍串行。

好处是能够看清失败在哪个子任务、需要重做哪份产物。代价是灵活性较低。要不要增加动态组队，应比较相同任务下的完成率、耗时和成本，而不是看角色数量。

## P0 与后续恢复分开

文稿把持续执行、过程可见和主动中止列入首期范围，但不承诺服务重启后的跨进程自动续跑。历史能显示，只能证明保存了历史；自动续跑还需要确认任务所有权、上次工具结果、审批和执行环境。

适合展示的证据是：同一任务的目标、过程、用户干预、工作区和文件成果。端侧与云端分别标明执行位置。未来补入实图时记录版本与日期，避免拿不同阶段页面拼出不存在的完整功能。
