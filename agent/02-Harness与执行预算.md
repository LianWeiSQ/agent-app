# Harness 怎样推进任务，怎样及时停止

依据：[会话讨论](sources/会话摘要.md)。下面是通用设计笔记，不声明某个当前框架采用了这些默认值。

## 问：Harness 的核心是什么？

它让模型的判断进入一个受控执行过程：准备上下文、调用模型、解析动作、检查权限、执行工具、把结果交回模型，直到完成或触发停止条件。

是否需要动态循环，要由任务决定。路径固定、验收确定的流程可以直接用程序编排。引入更多 Agent、反思步骤或规划器，应该有评测收益，而不是为了让系统看起来复杂。

## 问：150 多次工具调用，一定有问题吗？

单看数量不能判断。要先区分模型调用次数、调度 Step 数、工具调用次数和底层工具请求数。一次模型响应可以提出多个工具，一次工具内部也可能重试或分页。

复杂仓库任务读很多文件并不必然异常。值得警惕的是：同样输入反复获得同样结果、错误没有被消化、没有新证据却不断改计划，或者为等待外部作业频繁再调模型。

排查先列出调用分布：搜索、读取、执行、重试、轮询各占多少，哪一段开始没有进展。不要直接用小上限切掉所有长任务。

## 问：只加 max_steps 够不够？

不够。建议至少分别管理：

| 预算 | 防止什么 | 触发后的动作 |
| --- | --- | --- |
| 模型调用/Step | 无界推理循环 | 保存阶段结果，说明未完成项 |
| 工具数量与并发 | 扇出和工具洪泛 | 限制新动作，等待在途调用收敛 |
| Token 或费用 | 单轮上下文过重 | 裁剪、换策略或请求延长预算 |
| 墙钟时间 | 任务长期占用 | 区分主动执行与等待时间 |
| 单工具重试 | 故障被放大 | 有界退避；副作用动作先查结果 |
| 无进展窗口 | 原地打转 | 改变假设、请求信息或停止 |

阈值应按短问答、代码任务、长研究等任务类型配置，并记录触发原因。没有统一适用于所有 Harness 的“标准最大步数”。

## 问：怎么定义“没有进展”？

可观察信号包括新证据、产物版本、验证结果、未解决问题数量，以及工具调用的参数/结果摘要。仅比较模型措辞不可靠；也不能用内容哈希重复就断言循环，因为合理轮询也会重复。

在连续几轮没有新信息时提示模型总结卡点，并要求选择一个不同策略。仍无进展再停止或交给用户。具体窗口大小需要通过任务集校准。

## 问：长任务被停下，用户怎样继续？

区分可续的预算暂停和用户取消。预算暂停保存目标、已完成项、待办、产物引用、最后一个安全执行位置；继续时新增或调整预算。取消后不自动重新启动危险动作。

不能为了总结再无限调用模型。可以先用程序生成最低限度的终止记录，必要的最后总结也计入预算。

## 问：如何验收？

构造合理长任务、工具反复失败、循环搜索、长期审批、外部作业等待等场景。比较成功率、调用量、总耗时、人工打断率和误停率。目标是减少无效执行，而不是让全部任务看起来都很短。

与恢复衔接：[状态与副作用](03-持久状态与故障恢复.md)。

## 项目默认值怎样回答才准确

两份准备稿记录了不同入口和版本的默认值，不能选一个数字概括全部产品。先固定仓库与提交，再看入口默认、模板和请求覆盖、Runtime 最终解析及生产有效配置。仅看到 CLI 的 0，也不足以证明运行循环无上限。

这部分集中维护在[口径冲突表](interview/03-事实边界与证据.md)。默认值变化不影响这里的设计原则：逻辑 Step、实际尝试、工具调用和根任务总成本分别统计；网络重试即使不增逻辑 Step，也会消耗时间和可能的费用。

子任务并行前预留额度，完成后结算，不能让多个成员同时读到同一份剩余预算并超用。等待审批不占模型活跃时间，但算用户墙钟等待，保留的沙箱仍有驻留成本。
