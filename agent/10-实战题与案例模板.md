# 限时 Agent 项目怎样做成可验收的作品

来源：[会话中的限时项目讨论](sources/会话摘要.md)。题目来自用户提供的面试题截图，不能据此推断某家公司统一采用此流程；本页是准备方案，不是已交付应用。

## 练习：聊天截图转行动卡与建议

输入一张聊天截图及可选补充文字，识别可以创建会议、创建联系人、更新联系人的动作；用户确认后执行，并结合已有联系人与确认过的信息给出建议。

关键不在于把截图送给模型，而在于证据、确认、实际执行、记忆更新和结果解释能否连成完整流程。

## 第一版怎样划边界？

iOS 端负责导入图片、展示卡片、授权和结果反馈；后端或受控服务负责模型调用，密钥不写进客户端。联系人数据只按授权和必要范围读取，不为方便上传整个通讯录。

可先用 OCR 或多模态模型提取候选事实。为时间、姓名、联系方式附原文证据，无法确定时标记缺失，而不是生成看似完整的值。

## 行动卡至少包含什么？

- 动作类型与目标对象。
- 提议字段及各自证据。
- 缺失信息和冲突。
- 用户编辑、确认或拒绝入口。
- 当前版本、执行状态和失败原因。

“周五下午开会”缺少日期、时区或具体时间时，应结合可用上下文向用户确认。出现同名联系人，不能自动覆盖。

## 怎么体现 Agent，而不是单次抽取？

允许系统围绕缺失信息选择查询、请求补充、识别冲突、准备动作和验证结果。路径由观察结果变化，但动作集合和预算受限。没有必要为三个动作建立自由协作的多 Agent 集群。

提议、授权、执行是三个阶段。确认后参数若改变，应重新确认。重复点击或网络重试不能重复创建会议。

## Memory 怎样服务建议？

保存确认过的事实及来源、时间和作用域，例如一次联系信息更新；把模型推测与业务事实分开。建议应能说明它引用了哪些信息，信息不足时直接说不足。

不要把“朋友周五可能来”保存成确定会议，也不要把未经确认的截图内容长期记成联系人属性。

## 48 小时如何安排？

先做一条端到端链路：导入 → 候选卡 → 确认 → 一种真实动作 → 回读结果。随后再扩展另外两种动作和冲突处理，最后补权限拒绝、重复提交、失败重试与演示材料。

交付包含可运行环境、启动说明、测试样本、已知限制和真实演示。假数据与模拟外部操作应显式标注，不把 mock 演示说成系统已经接通。

## 最小测试集

截图模糊、无动作、相对时间、同名联系人、用户改卡片、拒绝权限、重复确认、外部成功但回包丢失、错误记忆纠正。对每个测试写预期结果，而不是只看界面有没有卡片。
