# 什么时候需要多 Agent，A2A 又解决什么

依据：[会话摘要](sources/会话摘要.md)、[A2A 官方概念入口](sources/公开参考.md)。

## 问：多 Agent 的收益来自哪里？

可独立验收的子任务可以并行，并让每个执行者保持较小上下文。也可以让一个独立检查者复核结果。但角色多并不自动带来更强推理，还会增加通信、重复调用、结果冲突和预算消耗。

先建立单 Agent 基线。只有任务确实可拆、合并规则清楚、评测证明收益时，再增加协作。

## 问：怎样委派才不会变成多人聊天？

给每个子任务明确目标、输入证据、允许访问的资源、预算、产物格式和验收标准。主任务保留最终责任，不把三个模型一致当成事实正确。

共享工作区需要写入规则。例如只允许不同子任务修改独立文件；同一文件的结果在集成阶段处理冲突。共享目标不代表共享全部上下文、全部密钥和无限权限。

## 问：失败怎么处理？

记录子任务身份、状态和输出版本。单个失败可以有界重试或重新分配，但先检查是否已有副作用。用户取消时传播到子任务，并查询仍在运行的工具或作业。

主任务的总预算应覆盖所有子任务。把成本拆到子线程不会让成本消失。能并行的也不应无限并行，模型、外部工具和沙箱都可能限流。

## 问：内部委派就是 A2A 吗？

不是。内部运行时创建子 Agent、发消息、等待结果，可以完全采用私有接口。A2A 是不同 Agent 服务之间的互操作协议，定义能力描述以及任务、消息和产物交换等概念。

所以看到 spawn、send、wait 之类动作，只能说明有委派机制，不能据此判断底层使用 A2A。某个产品是否实现标准，需要核对对应版本的公开接口或实现证据。

## 问：MCP 和 A2A 有什么区别？

可以先按交互对象理解：MCP 常用于模型应用访问工具、资源等外部能力；A2A 面向 Agent 服务之间的协作。一个远程 Agent 也可能通过普通 API 或工具被调用，边界并不由营销名称决定。

使用协议仍然需要鉴权、任务取消、超时、结果持久化和跨组织数据规则。协议互通不自动解决语义一致或外部效果去重。

## 怎么测值不值得拆？

同一任务集比较单 Agent、固定分工、有限并行三种方案。看成功率、总体与关键路径时延、总模型用量、集成冲突、重复动作和人工介入。收益不足时保留简单方案。
