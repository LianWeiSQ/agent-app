# 上下文、Memory 与长任务主线

依据：[Agent 会话总结](sources/会话摘要.md)。

## 问：Context 和 Memory 到底差在哪？

Context 是某次模型请求实际看到的内容。Memory 是希望跨步骤、跨任务保留的信息及其管理机制。把全部历史放进请求并不等于做好记忆，保存了向量也不等于信息真实、仍有效或允许使用。

还要区分业务状态：审批结果、工具执行状态、文件版本应有确定性记录，不依赖模型从摘要里猜测。

## 问：长任务怎样不跑偏？

用简洁工作态保留目标、约束、已完成项、当前假设、失败尝试、待解决问题和产物引用。每次执行后更新关键变化，重新组装下一轮所需内容。

例如排查项目启动失败，工作态应记录已经排除的原因和对应测试；否则压缩历史后，模型可能再次走同一条无效路径。

计划本身是可修订的假设。工具失败或者新证据与计划冲突时，先解释变化，再调整后续步骤，不能用执行旧计划替代完成目标。

## 问：压缩时必须保留什么？

- 用户目标、禁止项和授权范围。
- 已发生的外部副作用以及结果未知的动作。
- 关键证据的来源、版本与位置。
- 未完成问题、当前阻塞和恢复入口。
- 文件/产物的稳定引用。

普通工具输出可以先保留摘要和引用，需要时重新取回。超大输出不能直接塞进上下文；截断也要明确提示，避免模型把预览误当完整结果。

不要把压缩摘要当成绝对事实。重要状态回到数据库或原始产物核对，并对压缩前后使用同一类任务做回归。

## 问：怎样让 Memory 越用越有帮助？

先区分用户明确确认的偏好、业务系统里的事实、模型推测和一次性任务状态。每条可复用记忆记录来源、时间、作用域、有效性和撤销方式。

联系方式更新场景中，截图里出现的新号码只是候选信息。用户确认并成功更新联系人后，才记录这项变化；无法识别的归属不能悄悄合并到另一个同名人。

检索时先过滤用户/租户权限和时效，再判断相关性。旧记忆与新证据冲突，不能只因向量相似度更高就覆盖新信息。

## 问：缓存能代替 Memory 吗？

不能。Memory 服务于任务语义；Prefix/KV Cache 服务于推理复用。缓存命中不会自动让用户信息更正确，缓存丢失也不意味着知识消失。

保持系统提示与工具定义的稳定前缀可能有缓存收益，但不能为了命中率保留过期权限或错误事实。前缀缓存与实际推理延迟的关系见 [路由与 P/D](../infra/04-路由与PD分离.md)。

## 如何验证

用跨任务偏好、同名实体、过期信息、权限撤销、压缩后重复动作等用例检查。把事实正确率、无依据引用、误写记忆、任务成功率分别记录，不只看生成文本是否顺畅。

## 从项目问题走到统一装配

上下文太长只是现象。更深的问题是不同入口各自加附件、Skill 或历史消息，导致同一会话从不同入口继续时，模型看到的输入不一致。统一装配入口接收结构化来源，完成去重、顺序、配对和预算，再输出实际模型请求。

项目准备稿使用 ContextPackBuilder 描述这个职责。它不是一个万能摘要器，而是让每次请求能回答“这段内容从哪里来，为什么还在，为什么另一段被省略”。其中实现状态存在跨仓库口径差异，见[事实边界](interview/03-事实边界与证据.md)，不在本页宣称所有产品已经接入。

## 这些机制各解决一个什么问题

| 机制 | 要解决的问题 | 关键验证 |
| --- | --- | --- |
| 内容分类 | 用户限制与大段日志不能使用同一种删除策略 | 预算不足时仍保留硬约束 |
| 局部压缩 | 单次工具输出过长，又不能丢原文 | 展示变短、原文实际可读取、隐藏字段不重复携带全文 |
| 上下文检查点 | 用摘要替换历史后，不知道替换边界 | 记录有效版本与截止位置，恢复不重复注入旧历史 |
| 关键事实单列 | 摘要容易丢路径、禁令和已经确认的决定 | 来源有权威次序，工具新文本不覆盖用户授权 |
| 分层预算 | 一份长日志占满窗口，挤掉任务和输出空间 | 选择规则稳定，必须保留项超窗时明确失败或进入受控压缩 |

工具调用与结果还要成组处理，否则省下 token，却拼出了 Provider 无法接受的消息序列。相同来源、策略和版本的装配应可重放；模型生成的随机性另行评测。

## 一条能讲透的验证链路

准备一份必须读取原文细节的任务，同时加入“不得修改原始数据”的约束。工具返回长内容后，将全文保存、模型只见预览和引用；下一轮实际读取细节，生成产物，再检查原始数据没有改变。

接着在上下文检查点提交前后分别中断运行，核对恢复后的目标、禁止项、文件引用与工具配对。最终比较完成率、关键事实保留、输入 token 和总耗时。文本更短而任务变差，不算压缩成功。
