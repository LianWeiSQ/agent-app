# 持久化之后，任务怎样正确恢复

来源：[会话摘要](sources/会话摘要.md)。本章描述目标设计；没有证据时，不作为项目已完整实现的能力。

## 问：为什么不能把 Agent Loop 放在一个长 HTTP 请求里？

传输连接、用户任务和执行资源的寿命不同。页面断开不代表任务取消，模型断流也不代表工具没有生效。提交接口返回任务标识，后台执行者推进状态，事件订阅单独恢复，才能分别治理这些变化。

Worker 是推进任务的执行者，可以是协程、进程或独立服务。它是否独立部署不是关键；进程消失以后能否查到状态、谁允许接管才关键。

## 问：要存哪些状态？

| 对象 | 关键内容 |
| --- | --- |
| Session | 用户/租户、配置版本、工作区、会话关联 |
| Turn | 一次用户目标、状态、预算、取消标志、执行所有权 |
| Step | 步骤顺序、输入/输出引用、尝试次数、检查点 |
| Tool Call | 稳定调用标识、参数哈希、状态、外部结果引用 |
| Approval | 审批人、动作与参数版本、范围、期限、决定 |
| Question | 问题、选项或回答、等待状态、期限 |
| Effect Receipt | 已确认的外部结果、外部标识、核对依据 |
| Event | 单调序号、任务身份、供用户恢复查看的事件 |

聊天记录可以帮助理解过程，但不是所有权、授权和执行事实的唯一存储。

## 问：自动接管怎么做？

先通过数据库原子操作领取可运行 Turn，写入 owner、lease_until 和递增 epoch。执行者续租；接管者在租约过期且状态允许时获取新的 epoch。写状态时校验 epoch，阻止迟到的旧执行者覆盖新结果。

租约过期不等于旧进程已经死亡。fencing 还必须在真正受控的写入或执行入口生效；外部 API 不检查 epoch，就要依靠它自己的幂等键、查询或人工核对，不能把数据库锁说成全链路防重。

队列可以通知“有工作”，数据库记录才定义当前状态。重复投递需要无害，丢失通知可由扫描补偿。

## 问：为什么 Receipt 还不能保证恰好一次？

最危险的窗口是：外部动作成功，本地回执尚未写入就崩溃。数据库看不到成功，并不证明外部失败。

处理顺序是保存调用意图与稳定业务键，再执行；恢复时有回执就复用，没有回执先按外部业务键查询；支持幂等的接口可使用同键重试。参数变化不能复用旧键。

如果工具不可查询、不可幂等，结果应为 unknown，进入人工核对或约定补偿，不能盲目重做。补偿动作也不是天然可行，更不等于事务回滚。

## 崩溃恢复矩阵

| 故障位置 | 恢复依据 | 不能直接做什么 |
| --- | --- | --- |
| Bridge / Web 连接断开 | Turn 状态、事件 cursor | 把断线当成新任务重复提交 |
| Provider 输出一半 | 未提交模型步骤、已接收片段 | 把半段工具参数当成完整动作执行 |
| Tool 未发出前崩溃 | 持久意图、幂等键 | 为同一逻辑动作换一个新键 |
| Tool 已生效，回执未落库 | 外部查询、幂等结果 | 根据网络超时判断外部必定失败 |
| Approval 等待中重启 | 审批记录及动作版本 | 重新默许授权或丢掉原决定 |
| Question 等待中重启 | 问题与答复记录 | 只恢复提示文字，不恢复等待状态 |
| 旧 Worker 网络恢复 | epoch 与条件更新 | 接受旧执行者的迟到写入 |
| 沙箱被回收 | 工作区、环境版本、命令状态 | 声称内存中的程序无损续跑 |
| Storage 迁移失败 | 兼容策略、备份及恢复记录 | 只回退二进制就认定数据已恢复 |

## 问：审批和追问怎样不丢？

创建等待记录与 Turn 的等待状态应原子关联；决定的提交与唤醒需要可靠通知或可扫描补偿。审批绑定具体参数、作用域与有效期，重复点击返回同一决定。

批准不代表任何未来动作都被授权。执行前重新检查资源权限和审批有效性。用户取消与审批同到时，用状态版本明确谁先提交；已经失效的授权不能把 Turn 重新唤醒。

## 问：Storage 升级怎么回滚？

先扩展兼容字段，再迁移和双版本验证，最后才收缩旧结构。备份包括数据库以及必要的文件/产物一致性边界。回退服务时，要考虑新版本写入的事件类型、审批记录和产物引用，不能靠删掉新数据恢复“干净状态”。

演练在外部成功前后、审批提交前后、迁移中途注入故障。验证会话可查、等待不丢、已确认效果不重复、未知效果不误重试、新旧版本能按承诺读写。测试应在隔离环境使用假外部服务，不触发真实付款或通知。
