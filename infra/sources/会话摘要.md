# Infra 会话摘要与修正记录

来源：会话 **last dance -infra** 的独立讨论与已有本地学习材料。整理时间：2026-10-08。与 Agent 会话重复的职业背景只保留一份，不重复导出聊天。

## 讨论主线

1. 先理解模型推理的六个概念，再把请求链路串起来。
2. 区分推理引擎的单实例和整个推理平台。
3. 通过多卡案例理解 Pod、GPU、Rank、TP、副本与 P/D 分离。
4. 讨论 llm-d 与上层管理、网关、下层模型引擎的分工。
5. 从 Agent 工具执行走向沙箱平台，厘清模板、预热池、资源声明与实际 Pod。
6. 下探 CRI、containerd、runc、execd 的边界。
7. 讨论持久文件、执行结果未知、长等待、GPU 作业化和资源回收。

会话中用户明确说过“我们不部署，我们是用他的例子”。因此大型模型与多卡场景按教学分析记录，不改写为真实部署成果。

## 整理时修正的说法

| 旧讨论可能引起的误解 | 本库采用的口径 |
| --- | --- |
| GPU 任务都应离开沙箱 | 短时交互 GPU 任务可以在 GPU 沙箱运行；长作业是否独立管理取决于生命周期 |
| 8 张 GPU 就等于某个固定部署形态 | 必须先明确总卡数、每实例用卡、模型与精度、内存和并行方案 |
| 模型官方示例的卡数就是最低硬件要求 | 示例不是不可突破的最低配置，不能泛化到量化、卸载和其他版本 |
| P/D 分离一定更快 | 可能缓解阶段干扰，也增加 KV 交接、路由和资源成本 |
| 一个 Pod 等于一个模型副本 | 单个副本可跨进程与 Pod；多个 Pod 也可能只构成一个副本 |
| Controller 保存了状态就能恢复一切 | 需要实际资源对账、执行结果核对、存储与检查点支持 |
| namespace 或换目录就完成隔离 | 必须进一步验证权限、内核边界、挂载、网络、设备和密钥 |
| 沙箱控制面都属于 Harness | Harness 管任务语义；沙箱平台有自己的资源控制面与执行面 |

## 公开范围

内部沙箱实现曾被用于会话分析。本库仅保留抽象机制和通用验证方法，不发布内部源文件、未公开缺陷清单、架构原图或部署地址。教学图中的硬件配置与模型参数不作为本人的性能实测数据。
