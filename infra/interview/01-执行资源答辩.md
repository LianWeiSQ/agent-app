# Agent Infra 答辩：十二个高频追问

这页用于口头复习；详细机制在[创建与预热](../sandbox/01-创建预热与就绪.md)和[执行与恢复](../sandbox/02-命令文件与恢复.md)。回答中的方案不能自动换成“我们已经全部实现”。

## 1. 你说懂 Agent Infra，具体懂哪层？

我的主线是执行资源接入：模型提出动作以后，怎样把它放进有权限、工作区和资源边界的环境，执行结果怎样回到任务，文件怎样交付，最后怎样回收。模型服务接入也做，但推理引擎、多卡部署和底层 GPU 调优需要另拿实践证明。

## 2. 沙箱属于 Agent，还是 Infra？

两者在这里衔接。Harness 决定为什么执行、是否获准、结果如何影响任务；沙箱平台管理在哪里执行、能使用多少资源、环境何时销毁。任务状态与资源状态分开，才能分别处理服务重启和环境丢失。

## 3. 为什么不自己直接创建 Pod？

可以，但 Pod 只是计算载体。还需要生命周期、命令和文件协议、访问端点、租期、清理与对账。选现成沙箱能力是为了复用这些接口；仍需检查具体后端与现有平台的适配，不能把产品名称当成安全保证。

## 4. 怎么比较 OpenSandbox、E2B 与微虚拟机方案？

先分清执行运行层与完整平台，再比较现有 Kubernetes、身份、存储和运维体系怎样接入。真正做选型时，固定镜像和任务测首次可执行时间、空闲成本、恢复与网络越界，再看团队能维护哪条链路。

没做过对照试验，就讲适配理由和评估方法，不说“我们证明了某方案更快”。产品当前能力要看对应版本的[官方资料](../sources/公开参考.md)，本页不做实时功能排名。

## 5. 预热池有实例，为什么还可能执行失败？

预热资源可分配，不代表执行代理已经健康，工作区与依赖也可能没准备好。模板路径和预热路径都应做一次真实命令与文件读写验收。还要区分配置不匹配、无空闲容量和已分配但不可执行三种失败。

## 6. Controller 重启后怎么恢复？

它应读取持久的期望状态和实际资源重新对账，而不是靠某个没结束的 HTTP 请求继续。业务库和集群分别保存什么事实、哪些终态不可逆，要先约定。重启能继续 watch，不代表此前所有双写窗口都已解决。

## 7. 等用户审批，沙箱留不留？

看等待时长和恢复成本。短等待保留资源，长等待先保存状态与文件再考虑释放；重新建立环境不等于恢复原 Python 进程。后端不支持快照或暂停，就明确按重建策略设计，不假设一个 pause API 什么都能恢复。

## 8. 容器隔离是不是已经足够安全？

要看允许它影响什么，而不是只看用了 Docker 还是 Kubernetes。运行身份、特权、挂载、系统调用、网络出口、资源限制和凭据都要检查，再做跨任务和跨租户负向测试。模型提示词只能引导行为，不能做最终权限边界。

## 9. 命令超时，你会重试吗？

先确认命令是否还在运行、有没有已提交效果。能查询就用原命令身份查询，已完成复用结果，不能确认则保留未知。直接重发 shell 文本可能让两个进程写同一个文件。取消后还要检查子进程和实际资源是否退出。

## 10. 沙箱慢，怎么判断优化哪里？

先拆申请排队、调度、拉镜像、挂卷、初始化、执行代理就绪和真实命令耗时。运行后再看 CPU 节流、内存、IO、网络和下游。减少模型耗时不一定能解决安装依赖慢，预热也不一定能解决脚本本身慢。

## 11. 容量怎么估算？

分别看活跃任务、模型请求和沙箱驻留。稳定负载下平均并发约等于到达率乘平均驻留时间，得到的是平均量，不是峰值容量承诺。审批时保留实例，会延长沙箱驻留，却不增加模型活跃时间。

再通过混合长短任务与突发租户压测，观察排队、P95、失败率和单位成功任务成本。严格配额需要原子预占、失败释放和资源对账，不能只查一次当前行数。

## 12. 这些是你做的，还是团队做的？

可以回答：“我负责 Agent 侧执行需求与沙箱能力之间的架构边界、关键协议及联调验收。底层平台由团队协作完成。我会把本人设计和改过的部分、参与验收的部分、仅理解原理的部分分开说。”随后用一个真实文件或命令链路展开，不把熟悉代码等同于亲自实现。
