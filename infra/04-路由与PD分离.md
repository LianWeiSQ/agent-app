# 从单实例到路由与 P/D 分离

依据：[会话讨论及修正](sources/会话摘要.md)、[llm-d](https://github.com/llm-d/llm-d)、[vLLM 分离式 Prefill](https://docs.vllm.ai/en/latest/features/disagg_prefill/)。

## 问：vLLM 与 llm-d 谁负责什么？

模型引擎负责具体实例里的模型执行；llm-d 是面向 Kubernetes 的分布式推理服务栈，在模型服务之上组织路由与相关优化。

上层仍可能有租户、模型目录、计费和配置管理。平台使用了某个组件，不意味着整个平台就是这个组件。

## 管理请求和推理请求不要混淆

管理面接收部署规格、版本变更或副本调整，通过资源声明和 Controller 逐步收敛。推理数据面接收模型请求，选择健康实例并返回输出。

数据库里配置“两个副本”不代表两个实例已经加载完成。应分别记录期望状态、实际资源、就绪状态和观测时间。

## 问：为什么普通轮询可能不够？

不同请求的输入输出长度差别很大，实例的排队和 KV 空间也不同。只按请求数均分，未必均分了工作量。

Agent 多轮输入常有共同前缀，路由回缓存所在实例可能节省输入计算。但该实例排队很长时，等待成本可能超过缓存收益。路由是在负载、局部性与公平性之间权衡，不是永远黏在同一实例。

跨模型或版本切换要有单独规则。接口兼容，不代表上下文格式、工具能力和缓存状态兼容。

## 问：P/D 分离到底分了什么？

它分开 Prefill 和 Decode 两类计算负载，不是把模型前半层放在 P、后半层放在 D。常见部署中，两侧各自具备完成模型前向计算的能力，权重可以在各自实例内部再做模型并行。

Prefill 生成所需 KV 后，通过适配的传输与协调机制交给 Decode 继续生成。请求元数据、状态和必要的 Token 信息也要协调，不是只拷贝一块 GPU 内存就完成切换。

这是数据/计算依赖顺序，不表示控制请求必须先到 P。具体实现可能先选择 D，再协调远端 P。

## 问：一定更快吗？

不一定。分离可能降低长输入对持续生成的干扰，并允许分别调整容量；也新增路由、缓存交接、网络和资源占用成本。短输入、低并发或网络不合适时，可能得不偿失。

因此不能只报告“开了 P/D”。需要同负载比较 TTFT、ITL、完成率、吞吐和资源成本。一个阶段更快，另一个阶段可能开始排队。

## 问：需要多少卡？

先确定 P、D 每类实例在目标配置下需要多少资源，再决定各自数量。若作为假设，P 和 D 的每个实例都用 8 卡，1P+1D 就是 16 卡；这不等于所有模型都最低需要 16 卡。

1P+1D 是两种角色各一个，不自动形成阶段内高可用。能否采用不同并行布局、量化或硬件，要按具体引擎和 KV 传输兼容性验证。

## 什么时候值得开始研究？

先跑通单实例并测量瓶颈，再尝试多副本与普通路由，之后比较缓存/负载感知策略。只有已有证据显示阶段干扰或资源配比问题，才把物理 P/D 当成下一候选。

复杂部署不会自动改善 Agent 的工具等待、安装依赖和文件 IO。平台优化需要回到 [端到端容量分析](07-容量压测与故障定位.md)。
