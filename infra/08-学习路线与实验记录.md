# 从能听懂到能实操：Infra 学习路线

依据：[会话中的学习目标](sources/会话摘要.md)。尚未完成的练习保持“计划”状态，不因为文档写完就标记掌握。

## 第一步：加载一个适合现有硬件的小模型

先学习 tokenizer 将文本编码为 Token，Chat Template 将角色消息转换成模型要求的序列；同一组消息若套错模板，即使模型权重正确也可能得到差结果。

用 Transformers 完成加载和 generate，观察输入/输出 Token、结束条件与设备上的内存变化。选择兼容的模型和固定 revision，不默认下载最大模型，也不打开未经审查的远程代码执行选项。

FP16 与 BF16 都是 16 位格式，但指数范围与精度分配不同；是否可用、稳定及高效取决于硬件与软件。不能只因为占用字节相同就认为性能与数值行为一致。

输出：一份能复现的最小脚本、依赖版本和解释。不是 GPU 大规模部署履历。

## 第二步：把模型变成服务

在获准环境部署一个适合的推理引擎，验证模型加载就绪、请求格式、流式输出、取消、超时、错误和资源释放。

把服务接给一个最小 Agent 任务，分别测模型响应和整个任务时延。如果只有 CPU 或其他加速器环境，如实记录，不把它称作 NVIDIA GPU 实测。

输出：启动说明、固定请求样本、运行日志和已知限制。

## 第三步：做一次有对照的压测

先单请求，再逐步增加负载，区分短输入、长输入和长输出。记录 TTFT、ITL、成功率、排队及内存。

一次改一个主要因素，例如活跃序列限制或上下文长度。保留未优化版本，记录什么时候收益消失。具体操作参数必须按当前引擎文档核对，不照搬旧会话命令。

输出：条件完整的报告，而不是只有一张 GPU 利用率截图。

## 第四步：向平台层延伸

先理解 GPU 在容器和 Kubernetes 中怎样获得，再研究多副本、健康检查和路由。通过注入可控故障，验证新请求、已有请求和 Agent Turn 分别怎样受影响。

先做小规模可解释实验，暂不把 P/D、跨节点、多种量化和多 Agent 同时引入。下一步由当前瓶颈决定。

## 如果要走训练方向

训练比推理多出梯度、优化器状态、数据管道和检查点等成本。可以从小模型、少量经授权的数据与参数高效微调入门，但必须分开训练、验证和测试数据。

确认训练目标、评测标准、数据权限、显存与费用预算后再运行。训练 loss 下降不代表任务能力提升；需要对比原模型并检查其他任务退化。

本库当前没有证明大模型预训练或多机训练实践，因此这部分只保留入口，不堆砌成简历能力。

## 怎样判断自己学到了？

能解释为何慢、为何占显存、为何增加并发会改变延迟；能提供一个独立复现的小实验；能说出当前证据不能支持哪些结论。

优先把这些补齐，再决定是否深入 CUDA 算子。对当前 Agent/Harness 主线来说，首先需要读懂运行系统，不必同时转向底层算子开发。
