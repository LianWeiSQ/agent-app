# 容量不是一个并发参数：怎样压测与排障

依据：[Infra 会话摘要](sources/会话摘要.md)。公式与数字仅作分析方法，不是平台实测结果。

## 问：配置并发 32，能承载多少用户？

先问 32 限制的是入口请求、引擎活跃序列还是同时执行的任务。一次用户任务可能多次调用模型，中间又等待工具，无法从一个参数直接得到用户数或 QPS。

承载能力需要给出负载条件和服务目标，例如输入输出长度分布、到达方式、TTFT/ITL 上限和允许错误率。满足这些条件时能持续维持的负载，才是可用容量。

## 测什么负载？

包含短问答、长输入短输出、短输入长输出和真实 Agent 多轮请求。冷热前缀分别测试，记录环境是否预热、缓存是否命中。

并发递增适合观察系统何时恶化，但固定并发的闭环压测在服务变慢时会自然降低请求到达率，可能低估真实突发排队。还应按固定或突发到达率测，并同时统计拒绝和超时。

基线与候选固定模型、硬件、精度和主要参数；不要一次改模型、引擎、提示和负载，再把变化归因到其中一个参数。

## 报告必须包含什么？

硬件/软件版本、样本数、输入输出 Token、并发与到达率、成功/失败/拒绝/超时、TTFT、ITL 或 TPOT、端到端 P50/P95/P99、总吞吐、显存、队列、抢占及重试。

不要只统计成功请求的漂亮均值。低样本时尾部百分位不稳定，必须说明样本与持续时间。

## 容量估算怎样用才不误导？

稳定系统可用 Little 定律建立直觉：

```text
平均在途量 = 平均到达率 × 平均驻留时间
```

前提是统计同一系统边界、相匹配的流量和平均时间。把最大并发上限除一次请求时延，不能直接得到稳定 QPS。

分别用输入和输出 Token 吞吐估算能力，可以帮助发现约束；但 P、D 在同一实例共享资源时不能把各自孤立峰值简单拼成真实容量。最终需要混合负载测量。

换算到 Agent 任务，还要测每项任务平均模型调用量、工具等待和资源驻留。模型 GPU 与沙箱执行池应分别算。

## 排障表

| 现象 | 优先检查 | 不要急着下的结论 |
| --- | --- | --- |
| 首 Token 慢 | 网络、准入、队列、分词、Prefill、缓存 | GPU 一定不够 |
| 输出一顿一顿 | 调度、阶段干扰、网络回传、通信 | 只是前端渲染问题 |
| 显存满但利用率低 | 权重、KV、预留空间与实际负载 | 显存占用等于高计算利用率 |
| 并发升高后 OOM | 上下文、活跃序列、临时空间 | 只需增加重试 |
| 加卡后不快 | 并行方案、通信、拓扑、瓶颈迁移 | 卡数与速度线性对应 |
| Agent 慢但模型正常 | 工具、安装、沙箱、文件、审批 | 应该换更快模型 |
| 压测得分下降 | 环境、验证器、任务变化 | 模型能力必然退化 |

## 可重复的优化实验

提出一个假设，例如“环境准备占主要耗时”。测量阶段时间，尝试固定镜像或缓存，再比较相同任务。没有阶段数据前不要先决定优化 P/D。

取消和故障也要压测：请求取消后资源是否释放，实例重启后新请求是否路由正确，故障时是否发生重试风暴。所有实验在获准、隔离的环境中进行。
