# GPU、Pod、Rank、实例和副本如何对应

依据：[Infra 会话及更正](sources/会话摘要.md)、[Kubernetes GPU 调度资料](https://kubernetes.io/docs/tasks/manage-gpus/scheduling-gpus/)。

## 先把单位分开

| 名称 | 含义 |
| --- | --- |
| GPU | 计算设备资源，是否共享或切分由硬件与软件方案决定 |
| Pod | Kubernetes 调度与运行单元，一个 Pod 运行在一个节点上 |
| Rank | 分布式计算中参与进程的编号，不是必然等于 Pod 编号 |
| 模型实例 | 能协同执行一份模型推理的运行单元 |
| 服务副本 | 用于独立承接请求的一份模型服务复制 |

单节点八卡可以构成一个实例；跨两个节点的多个 Pod 也可以共同构成一个实例。此时任何关键参与者失效，都可能使整组不可用，不能把这些 Pod 数量当成高可用副本数。

## 问：多张卡怎样一起工作？

张量并行把部分计算拆分到多卡协同完成；流水并行将层按阶段划分；专家并行面向专家模型的分布。具体组合取决于模型、引擎和拓扑。

增加完整服务副本则是另一回事：请求分别路由到独立副本，主要增加总体承载或可用性，不自动把单个请求速度翻倍。

## 问：“8 张卡、两个副本、并发 32”够明确吗？

还缺：8 张是总资源还是每副本资源？32 是网关并发、实例活跃序列上限还是压测请求数？模型版本、精度、输入输出长度是什么？两个副本是否在同一故障域？

**纯假设示例：** 若一个完整实例确实需要 8 张卡，两个完整副本通常共需 16 张。若资源总共只有 8 张，就不能凭“副本数=2”让资源自动满足。这不是任何具体模型的最低卡数结论。

P/D 的两个阶段也不是普通的两个完整服务副本，见 [分离推理](04-路由与PD分离.md)。

## 问：GPU Pod 怎样获得设备？

节点需要可工作的驱动，容器需要合适的设备访问支持，设备插件将 GPU 资源暴露给 Kubernetes。工作负载声明资源需求，调度器选择符合条件的节点，容器运行时按平台配置提供设备。

能看到 GPU 不等于依赖兼容。驱动、容器环境、推理引擎、模型实现和精度方案要联合验证。

GPU 使用率低也不一定是调度没分配卡：可能是请求少、CPU 处理慢、网络输入慢或当前负载受访存限制。

## 问：多副本就高可用了吗？

要检查是否跨故障域、是否有剩余容量、路由何时摘除故障端点、请求能否安全重试。生成中的 KV 往往属于当前实例，重启后通常要重新计算；已向用户输出的部分文本也不能随意拼接成一次完整回答。

模型服务恢复与 Agent 任务恢复是两层问题。替换模型实例不能决定外部工具是否已经执行。

## 实验前的记录清单

模型 revision、精度、引擎/镜像、驱动、GPU 型号与数量、节点拓扑、并行配置、输入/输出长度、并发和超时。没有这组条件，显存和吞吐数字很难复用。
