# 从请求到输出：六个推理概念

依据：[Infra 会话](sources/会话摘要.md)、[公开资料入口](sources/公开参考.md)。这是概念链路，不要求每个实现按完全相同顺序部署组件。

## 从 Agent 发出的请求开始

用户只说“继续”，Harness 可能发送系统提示、工具定义、历史消息、文件片段与上一步结果。因此界面上的短输入，不代表模型只处理很少 Token。

概念链路是：组装输入 → 鉴权与路由 → 格式化/分词与准入 → 排队调度 → Prefill → Decode → 流式返回 → 释放请求资源。实际引擎可能在路由前后分词，也可能穿插不同请求的计算。

## Prefill：把输入处理一遍

对输入 Token 做前向计算，为后续生成建立状态。长输入通常增加这段工作，因此会影响首 Token 延迟。不能把它理解成把文本简单搬进显存。

Prefill 往往能并行处理多个输入位置，但仍受模型结构、序列长度、批大小和硬件影响。不要把“计算密集”当作任何负载下都不变的定律。

## Decode：基于已有上下文继续生成

标准自回归生成逐步计算下一个 Token，新增 Token 又成为后续输入。输出越长，需要经历的生成步骤通常越多；投机解码等优化可能改变每轮产出的 Token 数。

用户看到的流畅程度与 Token 间延迟有关，不只是请求完成时间。一个长 Prefill 插入进来，也可能影响其他请求的生成节奏。

## KV Cache：缓存的是中间状态

它保存注意力计算中可复用的 Key/Value，避免每一步都重新计算所有历史位置。它不是最终答案缓存，也不是用户的长期 Memory。

活跃请求越多、上下文越长，KV 占用通常越大。请求结束后的缓存保留、前缀复用与回收由引擎策略决定，不能笼统说全部立即删除。

模型权重能放进显存，只能证明加载可行；还要给 KV、计算临时空间和运行时预留容量。

## 批处理：让多条请求共同利用 GPU

静态批处理倾向等待一批任务成组执行。连续批处理在迭代之间允许完成的序列退出、等待的序列进入，提高不同长度请求混合时的利用率。

更多并发可能提高总吞吐，却使单请求更慢。调度还需要考虑 Token 预算与 KV 空间，不只是“凑够多少条请求”。

这与离线异步 Batch API 是不同层次的概念。

## 排队：模型没开始算，也会让用户觉得慢

请求可能等租户额度、可用实例、GPU 调度或 KV 空间。记录进入各阶段的时间，才能分清是资源不足、冷启动还是计算慢。

只对已经完成的请求统计延迟，会掩盖排队后超时和被拒绝的请求。端到端错误与拒绝应一起报告。

## 模型路由：选择什么模型，发往哪个实例

先确定允许使用的模型/版本和能力，再在候选实例中选择。短队列、可用容量、前缀缓存和故障状态都可能影响选择。

降级到另一个模型可能改变结果质量、工具格式或安全行为，需要策略授权及回归，不能仅因兼容 HTTP 接口就认为可无损替换。

## 如何判断到底哪里慢？

- 发出请求到首 Token：TTFT，包含网络、排队、预处理与 Prefill 等因素。
- 相邻输出 Token 的时间：ITL；平均生成时间可用 TPOT 描述，注意计算口径。
- 完整响应：端到端时延。
- 一段时间完成的输入/输出 Token：吞吐，必须说明是单请求还是整个实例。

Agent 总耗时还包括工具、沙箱启动、文件和审批。别拿整项任务墙钟时间除输出 Token，声称测出了模型解码速度。
