# 沙箱怎样承接 Agent 的执行与恢复

依据：[Infra 会话摘要](sources/会话摘要.md)、[OpenSandbox 入口](sources/公开参考.md)。本章抽象讨论，不公开内部实现细节，也不承诺某版本已经支持暂停、快照或完整授权治理。

## 问：沙箱属于 Harness 还是 Infra？

Harness 管这次任务为什么执行、是否允许、属于哪个会话、结果怎样进入下一步。沙箱平台有自己的资源控制面，管环境创建、容量、租约、状态和回收；执行面负责命令与文件操作。

两侧通过稳定 sandboxId、commandId 和产物引用衔接。业务服务不应把模型提出的任意集群操作原样转发给 Kubernetes。

## 一个文件分析任务怎样落地？

用户资料先进入有权限的存储或工作区。Harness 申请或绑定执行环境，确认就绪后发出受控命令。执行服务返回状态、输出和文件；大输出保存为产物引用。最终成果确认持久化后，才允许清理临时资源。

资源创建成功不代表命令成功，命令退出码为零也不保证报告满足业务要求，仍需要验收。

## 模板、Pool、资源声明和 Pod 的区别

| 抽象 | 回答什么问题 |
| --- | --- |
| 环境模板 | 镜像、命令、资源、挂载与端口应该是什么 |
| 预热 Pool | 提前准备多少可分配容量 |
| 资源声明，如 CR | 当前希望创建、更新或回收什么 |
| Sandbox 实例记录 | 平台怎样标识和查询这次环境 |
| Pod/运行时实例 | 实际承载计算的对象 |

这些不是普遍一对一，也不保证所有产品使用相同命名。Pool 存在不意味着有空闲资源；镜像、资源或挂载不匹配时，不应强行复用预热环境。

## 问：为什么需要 Controller 对账？

数据库记录业务意图，集群对象反映资源状态，两边更新通常不是同一个事务。只在 API 请求中“创建一下”无法覆盖进程崩溃和节点变化。

一种补强方案是保存 Operation 与确定性资源标识，提交资源后记录 UID/版本，再通过对账修复中间窗口。外部存在但本地未确认时先查询，不重复创建。删除也要追踪实际资源和数据保留情况。

这里描述设计方法，不把内部代码中的占位或缺口公开成生产结论。

## 问：execd 和容器运行时差在哪？

containerd 等组件负责把容器进程启动起来。execd 类执行服务运行在环境内部，接收后续命令、返回输出并提供文件操作等能力。命令执行不一定每次都通过 Kubernetes exec。

执行入口需要自己的鉴权与资源归属检查。execd 有接口，不表示可以直接暴露给公网。

## 问：等审批时资源要一直留着吗？

短等待保留环境可能降低恢复成本；长等待可保留持久工作区，释放计算，批准后按记录的镜像和配置重建。是否采用快照由后端支持、费用和恢复目标决定。

工作区恢复不等于 shell 变量、打开的连接和进程内存恢复。冻结进程也可能继续占用内存和设备，不能理解为免费暂停。

## 问：执行超时以后怎么办？

超时可能只发生在调用方，命令仍在执行。通过持久 commandId 查询状态；已完成读取原结果，仍运行则按策略等待或取消，无法判断保留 unknown。

取消请求被接受、进程组退出、外部副作用被补偿，是三个不同事实。不能因为前端显示取消就认定 GPU 和子进程已释放。

## 问：工作区与产物怎样保留？

临时工作区包含中间文件；已交付产物需要稳定标识、权限和保留策略。先确认文件写入及校验，再提交可访问引用；回收沙箱不应删除承诺保留的成果。

Pod 内临时存储不等于跨节点持久化。持久卷要考虑重挂载和访问模式；对象存储保留已上传文件，不保存程序内变量。

## 问：GPU 任务能不能在沙箱里做？

可以。短时交互式计算适合分配 GPU 的执行环境；持续很久、需检查点和独立重试的作业，可以交由作业系统管理，再由 Agent 保存 jobId、查进度和读产物。

分界是生命周期与治理需求，不是“有没有 GPU”。任务取消是否同时取消作业必须明确；训练续跑还需要程序自身的检查点。
