# 单个 vLLM 实例内部怎样工作

依据：[会话中的教学讨论](sources/会话摘要.md)与 [vLLM 文档入口](sources/公开参考.md)。没有在本次整理中实际部署模型。

## 问：“一个实例”是不是一个进程或一张卡？

不一定。这里把能共同完成一份模型推理的服务单元称为一个实例。它可以包含 API 进程、引擎调度逻辑和多个 GPU Worker；具体进程拆分随引擎版本及配置变化。

一个端口也不是可靠的实例计数：一个网关地址可汇聚很多实例，一个实例也可能有多个接口。讨论容量前先约定口径。

## 启动时发生什么？

确认模型与 tokenizer revision，解析配置和精度，加载权重，建立设备/并行通信，准备执行所需空间与 KV 管理，完成必要的初始化和预热，然后接受真实请求。

进程存在、HTTP 端口打开和模型可推理是不同状态。就绪检查应能反映初始化结果；否则流量进入尚未准备好的实例会触发超时。

启动失败要分清下载、访问权限、架构不支持、依赖不兼容、显存不足和多卡通信问题，而不是统一归因于模型。

## 一次请求由哪些部分负责？

| 部分 | 主要职责 |
| --- | --- |
| API 与输入处理 | 请求解析、模板、分词、参数与能力检查 |
| 引擎与调度 | 管理待执行/运行序列、计算预算和 KV |
| 模型执行 Worker | 在设备上执行模型，必要时做分布式通信 |
| 输出处理 | 采样、结束判断、解码与流式返回 |

这是职责划分，不是承诺每项都对应一个微服务。

## 显存都被谁用了？

权重只是其中一部分，还包括 KV、临时张量、执行图/工作空间、通信缓冲和内存分配器预留。GPU 显存已分配与正在有效计算不等同。

对普通 Transformer 注意力，KV 的直觉估算可写成：

```text
KV 字节量 ≈ 2 × 层数 × 已缓存 Token 数 × KV 头数 × 每头维度 × 每元素字节数
```

这只是逻辑总量近似，没有计算分块损耗、共享前缀、量化元数据及并行分布。GQA、MQA、MLA 等结构会改变存储细节，不能照一个公式推所有模型的实测显存。

## 分页 KV 和 Prefix Cache 是一回事吗？

不是。分页管理关注 KV 的分配与寻址；前缀缓存关注不同请求是否能复用相同前缀的中间结果。

命中前缀缓存通常减少重复输入计算，不意味着所有输出瞬间生成。复用必须满足模型、输入与隔离条件；缓存不能突破不同租户的权限规则。

## 改参数时先问什么？

上下文上限能否满足任务？同时活跃的序列是否挤占 KV？一次调度的 Token 预算是否造成长短请求干扰？显存使用比例是否留够运行余量？

记录参数与版本，单次只改少量关键因素，再看成功率、TTFT、ITL、吞吐、OOM 和抢占。不要照抄他人的最大并发值当作自己环境的安全容量。
