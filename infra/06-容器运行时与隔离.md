# 从 Kubernetes 到进程：运行时与隔离边界

依据：[会话摘要](sources/会话摘要.md)与 [官方资料入口](sources/公开参考.md)。

## 问：Docker 是 Kubernetes 必须依赖的组件吗？

不是。Kubernetes 可以通过 CRI 对接 containerd、CRI-O 等运行时。Docker Engine 并不是这条链路必须存在的一层；用 docker build 构建镜像，也不表示运行时必须使用 Docker Engine。

CRI 是接口约定，不是一个容器软件。容器的具体启动过程依赖运行时及配置。

## 一个常见 runc 路径

Pod 被调度到节点后，kubelet 通过 CRI 请求运行时。containerd 管理镜像和容器生命周期，CRI 集成配合网络插件准备 Pod 网络；shim 与低层运行时协作创建并管理容器进程。

runc 执行容器创建/启动等操作后可以退出；shim 留下处理进程生命周期、IO 和退出信息。这里只描述常见路径，不表示所有运行时都使用 runc。

沙箱管理器位于更上层，它提出资源需求；真正启动的容器又可能运行 execd 来接受后续命令。把它们分开，排障时才能知道问题停在哪一层。

## 问：换一个目录是不是沙箱？

不是。子进程默认仍能访问运行账号有权访问的资源。进程隔离要靠实际的 OS 限制，而不是告诉模型“不要访问外面”。

常用控制包括身份、文件挂载、namespace、cgroup、capability、系统调用限制和网络策略，具体能力因系统与配置而异。

本地进程沙箱可以利用操作系统规则限制文件影响，但文件限制不自动涵盖网络、设备、凭证和完整租户隔离。讨论 DSH 等具体实现时，要检查所用版本和平台，不套用其他系统的保证。

## 隔离层次怎样选择？

| 方式 | 主要考虑 |
| --- | --- |
| 普通子进程 | 启动轻，但不能只靠目录区分当作安全边界 |
| 受限进程/容器 | 利用 OS 机制，通常共享宿主机内核；强度依赖配置 |
| 用户态内核类方案 | 减少直接暴露的宿主机接口，需要验证兼容性和开销 |
| 虚拟机/微虚拟机 | 有更独立的内核边界，也有启动、设备与运维成本 |

不以名字直接给安全排名。特权模式、危险挂载、暴露管理 socket 和过宽凭证都会改变实际边界。

## 问：OpenSandbox、E2B、Firecracker 能横向等同吗？

它们处于不同抽象层：Firecracker 主要提供微虚拟机运行技术；E2B 提供更完整的沙箱平台体验；OpenSandbox 关注沙箱协议、生命周期和多种执行后端。

比较时先写需求，再检验协议兼容、控制面可维护性、执行环境、恢复、网络与成本。不能因为上游支持某运行时就宣称自己的部署已启用。

## 云上必须验证什么？

跨租户不能读写彼此的文件和资源；命令不能获得不该有的凭证；网络出口与云元数据访问受控；CPU/内存/进程/磁盘有合理限制；取消后后代进程能够收敛；回收不能影响其他任务。

Namespace 是资源与策略作用域，不是完整隔离保证。安全承诺应来自具体配置和负向测试，而不是架构图上的一个“安全沙箱”方框。
